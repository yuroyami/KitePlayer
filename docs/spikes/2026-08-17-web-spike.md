# The S6 web spike, measured

Run 2026-08-17 against KitePlayer `becbcba` and KiteFFmpeg `9b33480`, FFmpeg n8.0 as vendored at
`KiteFFmpeg/vendor/ffmpeg` (tag `n8.0`, commit `140fd65`). Toolchain: emscripten 6.0.6-git with
LLVM 24, node v26.7.0, macOS 26.6.1 on an Apple M2 (4 performance cores plus 4 efficiency cores).
Browser numbers are Chromium 148.

Nothing in either repository was modified. Every artifact lives in the scratch tree at
`<scratch>/W/wasm-spike`.

**Timebox result.** The box was 90 minutes of wall clock on the FFmpeg build. Four full lean
FFmpeg trees configured, compiled and installed in **5 minutes 20 seconds total** (06:39:40 to
06:45:00), a fifth variant later. Configure is the slow half at roughly 95 seconds per variant,
because emcc pays a Python start per probe; `make` itself is about 15 seconds per tree at `-j8`.
The build was never close to the box. This is worth recording on its own: the FFmpeg-to-wasm build
was assumed to be the risk in S6 and it is the cheapest thing in the whole item.

## Question 1. SIZE

**What was built.** The 17.6 `lean` set exactly: decoders `h264, hevc, aac, aac_latm, aac_fixed,
mp3, mp3float, mp3adu, mp3adufloat, flac` and the pcm family; demuxers `mov` (which is mp4, mov and
m4a) and `matroska` (which is mkv and webm); parsers `h264, hevc, aac, aac_latm, mpegaudio, flac`;
bitstream filters `h264_mp4toannexb, hevc_mp4toannexb, aac_adtstoasc, extract_extradata, null`;
protocol `file` only. No encoders, no muxers, no filters (`--disable-avfilter`), no devices, no
network, no third-party libraries, no zlib. Verified in the configure banner, not assumed.

The configure shape is `sharedCoreArgs()` cut to lean, plus the emscripten cross flags. Two
differences from the brief, both forced by FFmpeg n8.0 and both worth carrying into a real build
task:

- `--disable-postproc` **does not exist** in n8.0. Configure fails outright with
  `Unknown option "--disable-postproc"`. postproc is already off by default.
- `--disable-asm` **also disables wasm SIMD128**, because n8.0 gates simd128 as an arch extension.
  With `--disable-asm` the banner reports `ARCH c (generic)` and `HAVE_SIMD128 0`. A SIMD build must
  drop `--disable-asm` entirely; then the banner reports `ARCH wasm (generic)` and `HAVE_SIMD128 1`.

## Question 2. THREADS AND SIMD

Both configure and both link cleanly. All four combinations were built, linked and executed.

### SIMD

- **Configures cleanly**, but only after `--disable-asm` is removed. See Question 1.
- **Links cleanly**, runs in node and in Chromium.
- **Size delta: +162,445 B gzipped (+15.5%) over the single-threaded lean baseline.**
- **The delta is almost entirely swscale**: `libswscale.a` grows from 956,692 to 1,385,214 bytes
  (+45%), while `libavcodec.a` grows 8.9%.

**The finding that decides how to value SIMD.** FFmpeg n8.0 has almost no wasm SIMD. The entire
wasm SIMD128 source tree is four files:

```
libavutil/wasm/cpu.c
libavcodec/wasm/hevc/dsp_init.c
libavcodec/wasm/hevc/idct.c
libavcodec/wasm/hevc/sao.c
```

**There is no wasm SIMD for h264 at all.** This is measured, not inferred, and Question 3's numbers
match it exactly: SIMD buys about 3% on h264 and about 68% on HEVC. Paying 15.5% of the download for
3% on the codec that carries most web content is a bad trade today. It becomes a good trade the day
FFmpeg lands wasm h264 DSP, and that day arrives for free with an FFmpeg bump, which is precisely
what 17.4.9's wide-by-class read side was designed to capture.

### Threads

- **Configures cleanly.** Banner reads `threading support pthreads`, and the
  `WARNING: Threading support was disabled` line that the single-threaded builds emit is absent.
- **Links cleanly** with `-pthread -sPTHREAD_POOL_SIZE=8`.
- **Size delta on the wasm: +7,214 B gzipped (+0.7%). Size delta on the JS glue: +3,899 B gzipped**
  (the glue doubles, 14,989 to 30,445 raw, because it gains the whole worker bootstrap). Total
  +11,113 B gzipped, about +1.1%. **Threads are nearly free in bytes.** Their cost is entirely in
  deployment.

### The deployment constraint, stated plainly and then proven

`-pthread` compiles the module against `SharedArrayBuffer`. `SharedArrayBuffer` is only exposed to a
page that is **cross-origin isolated**, and a page is cross-origin isolated only when the server
sends both:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

This is **a constraint on whoever hosts the app, not on this codebase**. No amount of Kotlin or C
can work around it. It also spreads: `require-corp` means every cross-origin subresource the page
loads (fonts, images, analytics, embedded players, ad tags) must itself carry
`Cross-Origin-Resource-Policy` or a CORS grant, or it stops loading. For a library that other people
embed, that is a large ask, and it is an ask the library cannot satisfy on their behalf.

**Proven, not asserted.** The same threaded module was served from two local servers, identical
except for those two headers, and loaded in Chromium 148:

- With the headers: `crossOriginIsolated=true`, `SharedArrayBuffer=true`, the threaded module loads,
  and all thread counts run.
- Without the headers: `crossOriginIsolated=false`, `SharedArrayBuffer=false`, and the module dies
  during instantiation with
  `DataCloneError: Failed to execute 'postMessage' on 'Worker': SharedArrayBuffer transfer requires self.crossOriginIsolated`.

One detail worth carrying into any real implementation: **the failure mode is a hang, not an error.**
The rejection surfaces as an uncaught promise rejection inside the emscripten worker bootstrap; the
module factory promise never settles, so a naive `try/catch await` around it waits forever. The
single-threaded and SIMD modules on the same non-isolated page loaded and ran normally. A real web
artifact must feature-detect `self.crossOriginIsolated` **before** importing the threaded module,
not catch a failure after.

## Question 3. DECODE THROUGHPUT

**Method.** The whole clip is preloaded into wasm linear memory and served to `avio_alloc_context`
through in-memory C callbacks, so the number is decode, not I/O. Each measured pass decodes every
video frame in the clip through `av_read_frame` / `avcodec_send_packet` / `avcodec_receive_frame`
and touches two bytes of the luma plane per frame so nothing can be optimised away. One warm pass,
then 5 measured passes, all variants loaded in a single process and interleaved round-robin so that
CPU state drift hits every variant equally. Median reported. The interleaving matters: an earlier
non-interleaved run showed the same binary swinging between 141 and 328 fps as macOS moved the
process between efficiency and performance cores.

### 4K, which v1 states as a non-goal, for reference only

`KitePlayer/testmedia/hevc4k10.mp4`, HEVC Main10, 3840x2160, 178 frames.

Single-threaded 4K HEVC 10-bit lands exactly on 1.0x real-time on an M2, meaning it would fail on
anything slower. **The plan's decision to make 4K a stated non-goal of v1 is confirmed by
measurement.** It also shows where SIMD earns its 15.5%: +68% on HEVC, because HEVC is the only
thing FFmpeg n8.0 has wasm SIMD for.

### The answer

**Yes. 1080p30 real-time software playback in a browser is reachable, single-threaded, with no
SharedArrayBuffer, no cross-origin isolation, and no SIMD.** The measured headroom on real-world
High profile 1080p30 is **6.1x**, and on the plan's own clip **10.9x**.

**The honest scaling caveat.** An Apple M2 performance core is at the fast end of consumer hardware.
A mid-range x86 laptop or an Android phone browser is commonly 2x to 4x slower per core on this kind
of work. At 4x slower the High profile 1080p30 figure is still about 45 fps, which is still above
real time, but the margin for a low-end phone is thin and this spike did not measure one. What is
measured is that the decoder is not the bottleneck on desktop-class hardware. **The remaining risk at
1080p is not decode throughput; it is the per-frame draw cost, which this spike did not
measure because no wasm renderer exists to measure.**

## Question 4. THE INTEROP SHAPE, AND THE BLOCKER

### 4a. Why cinterop cannot be used, and what replaces it

`kiteffmpeg-core/src/nativeInterop/cinterop/ffmpeg.def` binds three headers
(`kitecodec_helpers.h`, `kitecodec_handles.h`, `kitecodec_abi.h`) and static-links `libkitecodec.a`.
cinterop is a Kotlin/Native facility. wasmJs is not Kotlin/Native, so **`ffmpeg.def` is unusable on
wasmJs and no amount of build wiring changes that.** `buildSrc` has zero occurrences of
`emscripten`, `wasm32` or `wasi`, and `TargetTriple` (`KiteFFmpeg/buildSrc/src/main/kotlin/FFmpegPaths.kt:146-175`)
has 11 entries, all of them konan targets. That enum is the wrong extension point: adding a wasm
constant to it implies a konan target that does not exist. A wasm build needs its own task, not a
twelfth triple.

The boundary to bind is **198 functions**: 191 `ffkmp_` in
`KiteFFmpeg/native/kitecodec-c/include/kitecodec_helpers.h` and 7 `kc_` in
`.../kitecodec_abi.h`, over 11 opaque handle types in `.../kitecodec_handles.h`. The baseline files
`native/kitecodec-c/exported-symbols-baseline.txt` (198 lines) and `signature-baseline.txt`
(213 records) are authoritative; `native/kitecodec-c/README.md:25-26` is stale and still says 188 and
195.

**The precedent already exists in the repo and should be copied, not reinvented.** The JNI adapter at
`KiteFFmpeg/native/kitecodec-jni/` binds the same 198 entry points in ~2,560 lines of C plus a
190-row `methods.def`, which is about 13 lines of glue per function. Its central design rule is
stated at `native/kitecodec-jni/kj_internal.h:16-20`:

> "HANDLES, NEVER POINTERS. Every C object crossing to the JVM travels as a generation-tagged token
> minted by kj_handles.c... A raw pointer in a jlong would turn every one of those caller bugs into
> memory corruption."

### 4b. The sketch (not implemented, by instruction)

**Handles.** In wasm32 every `kc_*` pointer is a 32-bit heap offset, so it marshals to a JS number
for free. That is exactly the raw-pointer design `kj_internal.h:16-20` rejects for JNI, and the
argument against it is identical here: a stale or double-closed offset becomes silent heap
corruption instead of a typed exception. The recommendation is to port `kj_handles.c` (202 lines) to
wasm and hand JS a generation-tagged integer token, keeping the C handle table on the wasm side. The
cost is one table lookup per call, which is nothing next to a decode.

**Memory ownership.** Three rules, all already stated in the C headers, all of which the JS side must
honour and none of which JS can enforce:

- Allocation pairs are fixed and asymmetric. `ffkmp_fmt_open_input_io` must be closed with
  `ffkmp_fmt_close_input_io` "and NOTHING ELSE" (`kitecodec_helpers.h:349-357`), because that close is
  the only one that frees the custom AVIO bridge.
- Some returns are borrowed and must never be freed: streams from `ffkmp_fmt_new_stream`
  (`:434-439`), metadata dicts (`:326-330`, `:378-382`), and `ffkmp_fmt_io_opaque` (`:371-376`).
- `ffkmp_strerror` returns thread-local storage that "must never be stored" (`:36-44`). A JS binding
  must copy it to a JS string inside the same call.

**Frames.** `ffkmp_frame_plane` (`kitecodec_helpers.h:605`) returns a raw plane pointer, which in
wasm is a heap offset that JS can wrap zero-copy as `new Uint8Array(Module.HEAPU8.buffer, ptr, len)`.
This is strictly better than the JNI path, which refuses the pointer entirely and copies the whole
frame through `nativeFrameCopyPlanes` (`native/kitecodec-jni/kj_frame.c:60-96`). It carries one
wasm-specific hazard the JVM does not have: **`ALLOW_MEMORY_GROWTH` detaches and replaces the
underlying `ArrayBuffer`, invalidating every outstanding typed-array view.** Views must be created
per draw and never cached across a call that can allocate. This suits KV-6's law 1 exactly, since the
frame is read only inside the draw phase anyway.

**Verified working, in a real browser.** The spike built and ran the whole shape end to end. The
harness serves `avio_alloc_context` from JS callbacks, with `-sFILESYSTEM=0` so no file protocol is
possible, and Chromium 148 reported:

```
kx_open -> handle 18348168   (avformat_open_input + find_stream_info over JS callbacks)
kx_pump decoded 120 frames in 670 ms  (179.0 fps)
frame size 1920x1080  luma plane ptr 39077360 stride 1920
zero-copy JS view over the Y plane: 1920 bytes, first 8 = [79,80,80,81,81,81,81,81]
seek back to 0s: 0
callback traffic: 77 reads, 8 seeks
kx_close ok
```

So open, demux, decode, zero-copy plane access from JS, seek and close all work over the exact
boundary shape `ffkmp_fmt_open_input_io` defines. **The interop shape is proven, not theorised.**

### 4c. The blocking read, and the answer to it

`KiteFFmpeg/native/kitecodec-c/include/kitecodec_helpers.h:336-337` says of the read callback:

> "It must BLOCK until at least one byte exists."

and `:338` says:

> "It is called from whatever thread drives the demuxer, one call at a time."

A browser **main thread** cannot block, so the naive shape is impossible. But the header does not say
"main thread", it says "whatever thread drives the demuxer", and that sentence is the way out. A
**dedicated Worker can block**, and the whole player belongs in one anyway. Inside a Worker there are
three blocking sources, in increasing order of capability:

1. **Fully buffered.** The bytes are already in wasm memory. The callback is a `memcpy` and never
   blocks. This is what the spike measured, and it needs nothing at all.
2. **`FileReaderSync`** for a `File` or `Blob` the user picked. Worker-only, synchronous, no headers
   required. This covers local playback, which is the same shape as Android's `content://` case.
3. **Synchronous `XMLHttpRequest`** for a URL. Worker-only, synchronous, **and it needs no COOP/COEP
   and no SharedArrayBuffer**. This is the streaming case.

Only if streaming is driven by a `fetch` pump on the main thread does the callback need
`Atomics.wait`, and only that route drags in SharedArrayBuffer and cross-origin isolation.

**The conclusion is the useful part: the blocking read does NOT force cross-origin isolation.**
Threads do. They are separable decisions, and the plan should treat them separately.

worker coroutines (`:3874-3888`, demux / videoDecode / audioDecode / audioFeed / videoSchedule) and a
raster lane (`:2600`), which park in `select` and `delay`, never in a blocking wait. The media clock
stores a drift offset and reads by addition (`internal/MediaClock.kt:28-32`), so there is no tick
thread to port.

**And the SPI is already the right shape.** `spi/VideoRenderer.kt:29` declares
`public suspend fun present(frame: VideoFrame, targetNanos: Long): Boolean`, and every method on
`spi/AudioSink.kt:23` is `suspend`. So a wasm renderer and a Web Audio sink implement suspending
methods directly on the event loop. **The `newSingleThreadContext` in `KiteVideoRenderer.kt:150` is
an implementation choice inside one renderer, not a contract the engine imposes.** A wasm renderer
simply would not make that choice.

**How big is the rework, honestly.** Not an engine rework at all. It is:

- **Zero hours** on `kiteplayer-core`, which already compiles and whose actuals are already written.
- **A new wasm `VideoRenderer`**, not a port of `KiteVideoRenderer.kt`. That file is 375 lines and
  its worker, dispatcher and two `runBlocking` joins are the part that disappears, replaced by direct
  suspending calls. It is a rewrite of the same 375 lines minus the threading, plus a Skiko draw path.
- **A new wasm `AudioSink`**, which does not exist for any target in a portable form.
- **`kiteplayer-ffmpeg` needs a wasmJs target and a replacement for `BlockingMediaIo.kt`.** That file
  exists to adapt a suspending `MediaIo` onto a blocking `MediaByteSource`, which is precisely the
  Question 4c problem, and the answer there (run in a Worker, use `FileReaderSync` or sync XHR)
  applies unchanged.

**W-12's premise should be amended in the register: the single-threaded-engine question is answered,
and the answer is that the engine is already single-thread-clean. The real S6 cost is the missing
wasm BACKEND (codec build, C ABI binding, audio sink, renderer), not an engine rework.**

## VERDICT

**Build S6. The spike clears its bar on every axis it was given, and one of the two blockers the
plan named turns out not to exist.**

The evidence:

1. **Size passes.** 1.00 MiB gzipped, 748 KiB brotli, for the full 17.6 lean codec set. That is a
   normal web payload, and it is smaller than the Compose runtime that will ship beside it.
2. **Throughput passes with room.** 6.1x real-time on High profile 1080p30, single-threaded, no
   SIMD, no SharedArrayBuffer, measured in both node and Chromium. The plan's 1080p target is met on
   the least capable configuration available.
3. **4K stays a non-goal, now with a number behind it.** Single-threaded 4K HEVC 10-bit runs at
   exactly 1.0x on an M2.
4. **The interop shape is proven working in a browser**, including zero-copy JS views over decoded
   luma planes.
5. **The engine blocker W-12 feared is not real.** `kiteplayer-core` already compiles to wasmJs, its
   actuals already exist and do not throw, its SPI is already `suspend`-based, and none of the
   `newSingleThreadContext` or `runBlocking` sites are in a web-targeted module.
6. **The build is cheap.** Four full FFmpeg trees in 5 minutes 20 seconds, against a 90 minute box.

**The order to build it in, and why:**

1. **Single-threaded, no SIMD, no cross-origin isolation, everything in one Worker.** This is the
   default artifact. It hits 1080p30 with 6x headroom, downloads at 1.00 MiB gzipped, imposes zero
   header requirements on whoever embeds it, and needs no `SharedArrayBuffer`. Ship this and web is
   real.
2. **Threads as a strictly optional second artifact**, feature-detected on
   `self.crossOriginIsolated` before import, never as the default. They cost +1.1% in bytes and buy
   3x, but they impose COOP and COEP on every host, and the failure mode without those headers is a
   hang, not an error. This is a nice-to-have for 4K and for slow devices, not a v1 requirement.
3. **Defer SIMD until FFmpeg has wasm h264 DSP.** Today it is +15.5% of the download for +3% on
   h264. Re-measure on each FFmpeg bump; the wide-by-class read side means the gain arrives for free
   when upstream lands it. If a build ever targets HEVC-heavy content, turn it on there and only
   there, where it is worth +68%.
4. **Drop hevc only if a sub-lean web tier is ever wanted.** It is 20.7% of the gzipped download,
   the single biggest lever inside the lean set, but it is also half the 17.5 matrix, so this is a
   tier decision for 17.6 and not a default.

**The one thing this spike did not measure, and it is the remaining risk.** KV-6, the per-frame draw
cost of KiteVideo on wasm through Skiko. There is no wasm renderer to measure, so nothing was
measured. Decode is proven to be 6x faster than needed; whether the draw path keeps up is the open
question, and it is exactly what 17.9's own KV-6 line says the S6 spike is for. **The honest S6 entry
condition is: the codec half of the spike passed, the renderer half is still unmeasured and should
be the first thing built and measured, before any of the binding work is committed to.**

**This exceeds 17.3's S6 estimate of 80 to 120 hours, and the planner should know that before
committing.** The gap is not in the parts S6 worried about. The codec build is 8 to 12 hours against
an assumption that it was the hard part, and the engine rework is zero hours against an assumption
that it was a blocker. The gap is item 5, the 198-function binding, which is 40 to 60 hours on its
own and which the original S6 sentence compressed into the phrase "the JS interop shape over the same
C ABI". The JNI adapter is the measured precedent for what that phrase actually costs.

Two ways to bring it back toward the estimate, both worth a decision rather than a silent choice:

- **Bind a subset, not all 198.** Playback needs demux, decode, frame access and seek. The encoder,
  muxer and filter-graph entry points are not needed for a v1 web player and are a large share of the
  191 helpers. A playback-only subset could plausibly halve item 5.
- **Generate item 5 from `signature-baseline.txt`.** 213 normalized declaration records already exist
  and are already gated in CI. A generator turns item 5 from authorship into review, and it keeps the
  binding honest against future ABI changes the way the baselines already keep the C side honest.
